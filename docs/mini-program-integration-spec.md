# 小程序接入工作台：前置规范与 UI 设计逻辑

> 适用范围：后续需要接入统一办公工作台（Vigor Workbench）的所有小程序/内部应用。
> 原则：**GitHub 是唯一事实源**；接入必须遵守本规范的认证、权限、数据边界与 UI 规范，验收以部署后的内网地址为准。

---

## 一、接入前置规范（必读）

### 1. 部署接入（第一步）

1. **同域反向代理**：小程序自身服务必须通过 Nginx 反向代理到工作台同域下的固定路径：
   - 路径约定：`/apps/<appId>/` → 小程序服务（如 `/apps/ai-sales-coach/` → 127.0.0.1:3xxx）。
   - 理由：同域 iframe 内可直接复用工作台会话（Cookie），无需额外登录。
2. **网关地址配置**：在工作台根目录 `.env` 配置 `VITE_APP_<APPID>_URL=/apps/<appId>/` 后重新构建前端。
   - 严禁使用 GitHub Pages、第三方站点或外网地址做内嵌。
3. **iframe 嵌入**：工作台以 iframe 嵌入小程序页面，身份随同域 Cookie 自动传递。

### 2. 应用注册与权限

1. **应用清单注册**（两处必须同步）：
   - BFF：`apps/bff/src/apps.service.ts` 的 `seed` 应用列表。
   - 前端：`src/data/workbench.ts` 的 `apps` 数组（id / name / 所属部门 department / description / urlEnv / access 内置岗位 / state）。
2. **岗位权限**：「岗位与权限」页（管理员）为每个应用配置可访问的岗位；服务端持久化到 `app-permissions.json`，接口 `GET/PUT /api/admin/app-permissions`。
3. **访问校验**：工作台前端按「当前账号岗位 + 应用权限」过滤入口；BFF 侧 `GET /api/apps`、`/api/apps/:appId/api-services` 也会按岗位校验，未授权返回 403。

### 3. 身份与会话

| 场景 | 方式 |
| --- | --- |
| 工作台内嵌（同域 iframe） | 直接调用 `GET /api/auth/session`（携带 `vigor_session` Cookie）取当前用户；无需二次登录 |
| 登录 | `POST /api/auth/login`（账号/密码）→ 下发 `vigor_session`（HS256 JWT，8 小时） |
| 独立服务端需代用户调用 | `POST /api/auth/bridge` 换取桥接令牌（当前仅对 `ai-sales-coach` 开放，其余需扩展白名单） |
| 请求身份 | Cookie `vigor_session` 或 `Authorization: Bearer <token>` |

### 4. API 接入（小程序调用工作台能力）

1. **服务注册**：「服务与授权 → API 服务库」创建服务（名称 + 访问密钥）；**密钥只保存在服务端**，前端/小程序/日志不得出现明文。
2. **授权**：「服务与授权 → 应用 API 授权」把已启用服务授权给指定小程序。
3. **小程序读取自己的服务**：`GET /api/apps/:appId/api-services`（仅返回已授权且启用的服务）。
4. **代理调用**（AI 类能力示例）：`POST /api/apps/:appId/ai/chat/completions`，请求头携带：
   - `X-Workbench-App-Id: <appId>`
   - `X-Workbench-App-Secret: <小程序侧的应用代理密钥>`
   工作台 BFF 校验通过后代理到配置的 endpoint。

### 5. 数据边界与安全

- 小程序**禁止直连**工作台数据库 / COS / 内部服务；一切能力通过工作台 BFF API 与事件接入。
- **禁止在任何前端代码、仓库、日志、聊天中暴露** BFF/DB/COS/API/SSH 密钥与 `ORG_PICKER_TOKEN`。
- 跨系统数据只允许通过 API、事件与映射表接入，不允许互相直接写库。
- 当前部署为**内网测试环境**，禁止放入真实敏感数据。

### 6. 人员选择器（如小程序需要选人）

1. 打开独立小窗：`window.open('/org-picker?mode=single|multi&title=选择人员&token=<ORG_PICKER_TOKEN>', '_blank', 'width=420,height=560')`。
2. 用户在弹窗内确认后，弹窗向调用方发送：`window.opener.postMessage({ type: 'vigor.org.picker.result', mode, persons }, '*')` 并自动关闭。
3. **调用方必须校验 `event.origin`** 后再使用返回数据；`persons` 结构：`{ id, department, team, role, name, englishName }`。
4. 数据接口 `GET /api/org/tree`、`/api/org/persons` 支持 `X-Picker-Token` 请求头鉴权。

### 7. 接入自检清单

- [ ] 小程序已同域代理到 `/apps/<appId>/`，`.env` 已配置 `VITE_APP_<APPID>_URL` 并重新构建
- [ ] 应用已注册进 BFF `apps.service.ts` 与前端 `workbench.ts`（id 唯一、部门归属正确）
- [ ] 已在「岗位与权限」配置可访问岗位
- [ ] 内嵌页能通过 `/api/auth/session` 拿到当前用户
- [ ] 需要调用的 API 已在「服务与授权」创建并授权，代理调用带 `X-Workbench-App-Id/Secret`
- [ ] 需要选人的功能已接入 org-picker 协议并校验 origin
- [ ] 无密钥泄漏、无直连数据库、UI 符合下文设计规范

## 二、UI 设计逻辑（接入方必须遵循的视觉与交互规范）

### 1. 设计语言（Design Tokens）

**色彩**
- 品牌深色：`#15202c`（侧边栏/弹窗头部/深色主按钮背景）
- 品牌红（强调）：`#d92d20`；文字红 `#a61b14/#9b251d`；浅红底 `#fff0ee/#fff4f2`
- 正文：`#1b2430`；次级文字：`#61798a/#8a97a1`
- 页面背景：`#f3f3ef`；卡片白 `#ffffff`；边框 `#d8d9d4/#e3e6e1`
- 成功绿：`#24643b` + 底 `#edf7ef`；警告金：`#92610c` + 底 `#fdf3dc`
- **部门强调色（全站统一，勿另造色）**：
  `总经理办公室 #b45309 · 人力总经办 #0d9488 · 销售部 #2563eb · 采购部 #16a34a · 销售支持组 #7c3aed · 市场运营组 #ea580c · 船务部 #0891b2 · 财务部 #e11d48`
- 部门色用于：部门色块、卡片顶部 3px 强调条、负责人头像、组织架构图区块顶边。

**字体**
- 正文：`Noto Sans SC`；等宽/编号/代码：`DM Mono`。
- 字号：标题 16-18px、正文 13-14px、辅助 11-12px、等宽小字 10-11px。

**几何**
- 圆角：卡片/区块 12-14px，输入/按钮 7-8px，徽标/胶囊 999px。
- 阴影：卡片轻阴影 `0 1px 3px`；弹窗重阴影 `0 24px 60px`。

### 2. 布局逻辑

- **侧边栏**：桌面端默认折叠为 72px 图标栏；**鼠标悬停展开 246px、移出折叠（延迟防抖）**；汉堡按钮可固定/取消固定；折叠态图标悬停显示 tooltip；激活项左侧 2px 红色竖条。移动端（≤960px）为抽屉 + 遮罩。
- **顶栏**：60px，左侧汉堡 + 面包屑（VIGOR / 页面），右侧搜索/通知/当前账号。
- **页面结构**：`.page-heading`（标题 + 一句说明 + 右侧主操作按钮）→ 页内标签 `.api-tabs`（如「账号列表 / 字段管理」）→ 内容卡片区。

### 3. 组件规范

| 组件 | 规范 |
| --- | --- |
| 主按钮 | 深色实底（`#111315/#234861`）、白字、圆角 8px |
| 危险按钮 | 红描边红字，悬停红底白字 |
| 文字按钮 | 下划线小字（`.text-action`），用于次要操作 |
| 表单 | `label`（12px 加粗）+ 输入框（高 40px、圆角 8px、focus 红色描边）；下拉 `select` 同风格 |
| **弹窗** | 全屏半透明遮罩 + 毛玻璃；内容框**统一宽 460px 居中**、圆角 14px、入场动画；用途：新增/编辑账号、重置密码等小窗 |
| **Toast 提示** | 顶部居中浮层，成功绿/错误红，约 3 秒自动消失；用于所有操作反馈 |
| 账号卡片 | 首字头像 + 姓名 + `@用户名` + 徽标行（岗位灰/管理员红/部门主管金/状态）+ 右侧操作列 |
| 部门区块 | 卡片顶部 3px 部门色强调条 + 部门色块 + 负责人头像 chip + 人数 |
| 徽标 | 岗位（灰底）、管理员（红底）、部门主管（金底）、已启用（绿）/已停用（灰） |
| 行列表 | 色块 + 名称 + 次级信息 + 操作按钮；支持**行内编辑**（输入框 + 保存/取消，Enter/Esc） |
| 空/加载/错误态 | 空列表占位文案、加载中提示、错误红条或 toast |

### 4. 交互逻辑

- **部门顺序全站统一**：总经理办公室 → 人力总经办 → 销售部 → 采购部 → 销售支持组 → 市场运营组 → 船务部 → 财务部（组织架构图、账号页、选择器一致）。
- **岗位显示以账号为准**：任何页面展示岗位，必须与账号权限页一致（改名/自定义岗位全站同步）。
- **删除保护**：正在被使用的部门/小组/岗位删除时给出明确提示，禁止静默失败。
- **表单内联新增**：「＋新增小组/岗位」用行内输入，不在系统弹窗中打断操作。
- **独立小窗**（如人员选择器）固定 420×560 并在屏幕居中。
- 所有数据操作成功后以 toast 反馈，错误以红色 toast 反馈。

### 5. 一致性要求（验收红线）

1. 色彩、字体、圆角、按钮/表单/弹窗/toast 必须与上述规范一致，**不引入新的部门色或品牌色**。
2. 岗位/部门命名与工作台完全一致，不出现同一概念两种叫法。
3. 嵌入页头部可保留小程序自身品牌，但整体视觉（导航、弹窗、反馈）需与工作台协调。
4. 交互反馈（成功/失败/删除保护）必须有明确提示，禁止无响应的按钮。
